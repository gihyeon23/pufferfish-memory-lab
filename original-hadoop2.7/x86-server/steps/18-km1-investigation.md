# 18. KM1 메모리 과다 원인 조사 (2026-11-24~, 이슈 #58)

## 목적

11-20 랩미팅 피드백 "KM1이 너무 많이 쓴다". 논문 KM1 최대 약 28GB(노드 23%, 수요의 약 46%) vs 우리 G-2 13.5~14.2GB(노드 48~51%, 단독 수요 거의 전부).

## 방법 (단계)

1. 기존 로그 집계 (G2-r1~r4, G3-r1) — `setup/km1-timeline.py`
2. 코드 읽기: kill 뒤 회수 메모리 배분, EJF
3. 판단 로그만 추가한 빌드로 G-2 1회
4. 조건 하나씩 바꿔 실행 (2~3 결과 보고 사용자 결정)
5. 재현 3회 → `common/lab-meetings/2026-11-27/` 정리

|---|---|---|---|---|
| G2-r1 | 289s, 18% (KM2) | 10.1GB | +5.7 / +1.0GB | 115s |
| G2-r2 | 288s, 18% (KM2) | 10.3GB | +5.6 / +0.9GB | 109s |
| G2-r3 | 288s, 16% (KM2) | 10.7GB | +4.4 / +1.8GB | 126s |

| G3-r1 | 293s, 18% (KM2) | 10.2GB | +4.8 / +1.9GB | 137s |

- 5회 모두: 첫 kill(KM2) **0.4~0.9초 뒤** KM1이 약 +3.7GB 한 번에 puff (예 G2-r1 17:36:11.313 kill → 17:36:11.716 10088→13911MB)
- 그때 PR은 RUNNING(OCM 아님) → puff 대상 아님. 풀린 메모리를 KM1이 가져감
- KM1 suspend는 초반 1~2분뿐, 이후 RUNNING. 논문은 "container-2 and 3 suppressed at the beginning" [p.265], 첫 kill 약 600초(우리 약 290초)
- **추측**: 첫 kill이 이르고, 그 직후 OCM인 것이 KM1뿐이라 KM1이 단독 수요만큼 커짐. 논문은 KM이 kill 전까지 오래 억눌려 23%에 머문 것으로 보임 → 2단계(코드)에서 확인

## 2. 첫 kill이 일어나는 경로 [실측 + 코드]

- 논문 Alg.1 [p.264]: C = OCM 컨테이너 집합(우선순위 순, 2분 동안 OCM 아니면 C에서 빠짐 [p.264]). `A ≥ M`이고 **C의 첫 번째**가 OCM → C의 마지막 kill
- 코드: C의 첫 app(`swappingContainer.get(0)`)이 OCM이면 kill (`NodeMemoryManager.java:276-301` + `setup/patches/alg1-kill.diff`) → **논문 글자 그대로와 같음**
- 5회 모두 같은 순서 (nm.log):

| 회차 | 노드 꽉 참 | PR 마지막 OCM | PR이 C에서 빠짐 = 첫 kill(KM2) |
|---|---|---|---|
| G2-r1 | 17:34:51 | 17:33:44 | 17:36:07.512 (같은 ms) |
| G2-r2 | 08:58:23 | 08:57:06 | 08:59:25.766 |
| G2-r3 | 09:26:01 | 09:25:11 | 09:27:25.260 |
| G2-r4 | 09:56:15 | 09:54:00 | 09:56:43.682 |
| G3-r1 | 11:33:56 | 11:33:21 | 11:35:30.928 |

- 흐름: PR이 OCM 아님(사용 7.4GB < limit 7.9GB, 약 6분 정체) → 2분 뒤 C에서 빠짐 → C 첫 번째 = KM1(OCM) → KM2 kill → 풀린 메모리 KM1 puff
- PR 증가 모양 차이 (노드 대비):

| | 400초쯤 PR 사용 | 단독 수요 |
|---|---|---|
| 논문 (그래프 읽기) | 39GB / 120 = 33%, puff 계속 (53GB) | 약 60GB (50%) |
| 우리 G2-r1 | 7.4GB / 28 = 26%, 17:34~17:40 정체 | 14GB (50%) |
| 우리 단독 PR (G1b) | 약 8GB에서 정체, 수요의 대부분은 후반(60% 시점 이후) | — |

- KM 단독(G1b)은 시작 3.4분에 12.3GB(수요 90%) — 앞쪽에 몰림
- **추측**: 논문 PR은 앞쪽에서 계속 OCM이라 C 첫 번째를 지키고, puff를 먼저 받아 KM1이 23%에 막힘. 우리 PR은 수요가 뒤쪽에 몰려 초반에 C에서 빠지고, 그 자리를 KM1이 차지 → kill·puff가 KM1 쪽으로 감. 코드 동작은 논문 Alg.1과 같고, **차이는 PR의 메모리 증가 모양(워크로드)**
- 3단계(판단 로그 추가 빌드)는 불필요 — C 출입(`add swapping container`, `is removed`)이 이미 nm.log에 있음
