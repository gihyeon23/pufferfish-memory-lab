## 3. 꼭 짚을 포인트

### 3-1. 원 코드 빌드 — "테스트 코드" 1곳 컴파일 오류 (★ 이번에 말할 것)

- **결론: Pufferfish 실행 코드는 수정 없이 컴파일 성공. 실패하는 건 같이 들어 있는 테스트 코드 1곳뿐이고, 실행에는 영향 없음** [실측]
- 원 저자 저장소의 코드 두 종류

  | 종류 | 위치 | 역할 | 컴파일 |
  |---|---|---|---|
  | 실행 코드 | `src/main/` | 실제로 도는 Hadoop + Pufferfish (OCM 감지·suspend·puff·reclaim) | ✅ 성공 |
  | 테스트 코드 | `src/test/` | 개발자 점검용 단위 테스트. 실행용 Hadoop에는 안 들어감 | ❌ 1곳 실패 |

- 오류 내용 [원 구현]
  - 원 저자가 `RMNode` 인터페이스에 메서드 2개 추가: `getCurrentActualMemory()`, `getCurrentRealMemory()`
  - 테스트용 가짜 객체 `MockNodes.java`에는 **1개만 추가하고 1개를 빠뜨림** → `MockNodes.java:99` 컴파일 오류
  - 추가된 1개도 `return 0; // TODO Auto-generated method stub` (IDE 자동 생성 그대로)
  - [추측] 원 저자도 테스트를 건너뛰고 빌드했을 것
- 왜 문제가 되나
  - Hadoop 공식 빌드로 **실행용 묶음(tar.gz)**을 만들면 묶는 과정에서 테스트 jar까지 요구함 → 테스트 오류 1곳 때문에 마지막 묶음 단계만 실패
  - 비유: 제품(실행 코드)은 완성, 포장 공정이 "검사지(테스트)도 같이 넣어야 포장 완료" — 검사지 한 장 오타로 포장만 안 됨
- 대응: **원 코드는 한 글자도 안 고친다**
  1. 테스트를 건너뛰고 원 저자 코드 컴파일 → YARN jar 10개 확보 ✅
  2. 공식 Apache Hadoop 2.7.3 실행용 바이너리를 받아 그 안의 YARN jar만 원 저자 것으로 교체 (진행 예정)
  - 근거: 원 저자는 YARN 모듈만 수정, HDFS·Common·MapReduce는 무수정 [원 구현: `git diff 86ae43c HEAD`]
  - 추가 검증 예정: 원 저자 소스로 빌드한 HDFS·Common jar와 공식 바이너리 jar 비교 → 같으면 "공식 바이너리 + 원 저자 YARN jar = 원 저자 소스 전체 빌드"
- 검토했지만 안 한 방법: 테스트 파일에 빠진 메서드 6줄 추가 → 실행 동작은 같지만 **소스가 원본과 달라져서** 제외
- 발표 문장 예: "논문이 공개한 코드의 실행 부분은 수정 없이 그대로 빌드됩니다. 같이 들어 있는 테스트 코드 한 곳에 원 저자 실수가 있어 테스트는 건너뛰었고, 실행에는 영향이 없습니다."

### 3-2. 원 코드 = 논문 공식 구현

- [논문] p.263: "We have open-sourced Pufferfish at: https://github.com/yncxcw/pufferfish."
- [원 구현] 마지막 코드 변경 2018-02-05, 이후는 README 수정뿐 → 논문(2019) 전에 코드 확정
- 단, 논문의 SJF 정책은 코드에 없음(EJF만) [원 구현]

### 3-3. Docker 1.12.1 — 논문과 같은 버전

- Ubuntu 16.04 저장소에는 1.10.3 / 18.09.7만 있음 → **Launchpad 보관소의 2016-10-14 arm64 빌드** 사용 (containerd 0.2.3, runc rc1 같은 날 세트) [실측]
- 원 코드가 쓰는 cgroup v1 경로·`--oom-kill-disable`·`docker update --cpu-quota/--cpuset-cpus/--memory` 모두 동작 확인 [실측]
- 16.04 커널은 swap accounting이 기본 꺼짐 → `swapaccount=1`로 켬 (원 코드 OCM 판정이 swap 사용량을 읽음) [실측]

### 3-4. task 이미지 — 유일하게 소프트웨어에서 못 맞춘 부분

- OS가 두 층: **바깥(VM) = Ubuntu 16.04 (논문과 같음)**, **안쪽(task 컨테이너) = 논문은 CentOS 6.5 + JDK 7**
- 원래 이미지 `sequenceiq/hadoop-docker`를 못 쓰는 이유
  - x86 전용 [실측: Docker Hub]
  - Docker 1.12.1이 지금 Docker Hub에서 이미지를 못 받음(`missing signature key`) [실측]
- CentOS 6.5는 ARM판 자체가 없음 (보관소에 i386·x86_64만) [실측]
- 현재 구축: **Ubuntu 16.04 + OpenJDK 8 + Hadoop 2.7.3** 이미지 (`local/hadoop-docker:2.7.3`) [실측, 05 §5]
  - 원 저자 실제 사용 이미지는 `sequenceiq/hadoop-docker:2.4.0` [원 구현: README] → 안쪽 Hadoop도 2.4.0
- ⚠️ **JDK가 7 → 8로 바뀐 것이 가장 큰 차이** — Pufferfish가 감시하는 컨테이너 메모리 구성이 달라짐(PermGen → Metaspace) [추측]
  - ARM64용 OpenJDK 7 확보 가능 확인 (Ubuntu 14.04 7u211 / CentOS 7 1.7.0.261) [실측] → JDK 7 이미지로 바꿀지 확인 요청 (§5)
- Pufferfish 동작 자체는 컨테이너 바깥(NM + cgroup)이라 이미지와 무관 [원 구현]
  - 단, 원 코드가 Flex 컨테이너 `-Xmx`를 64GB로 치환 → **JVM 힙 확장 패턴이 OCM·puff 횟수를 좌우** → JDK가 입력을 바꿈 [추측, 05 §7]
  - 결정: **JDK 7 계열(CentOS 7 + OpenJDK 7)로 진행**, JDK 7/8 비교로 영향 실측 예정

### 3-5. 영향 정리 (결과에 미치는 영향 큰 순서) [추측]

| 차이 | 영향 | 맥에서 줄일 수 있나 |
|---|---|---|
| 하드웨어 규모 (26노드·128GB → VM·3GB) | 큼 | ❌ 비율만 유지 |
| CPU (x86 → ARM) | 중간 | ❌ |
| JDK (Oracle 7u71 → 현재 OpenJDK 8) | 중간 | ✅ ARM64 OpenJDK 7 확보 가능 |
| 네이티브 라이브러리 없음 | 중간 (I/O 작업) | ✅ ARM 빌드 시도 |
| 안쪽 Hadoop (2.4.0 → 2.7.3) | 작음 (MR task 쪽만) | ✅ 2.4.0 이미지 가능 [추측] |
| 안쪽 OS (CentOS 6.5 → Ubuntu 16.04) | 작음 | ⚠️ CentOS 7까지 |

- 따라서 성능 **절대값**은 논문과 직접 비교 불가 → 같은 환경에서 "YARN만 vs YARN + Pufferfish" **상대 비교**로 경향 확인이 목표

| 공식 바이너리를 섞어도 원 구현과 같은가? | 같다. Common·HDFS·MR 약 7,300 class를 시그니처 비교 → 차이 4개는 전부 컴파일러 자동 생성 `access$` 메서드(JDK 7/8 차이) [실측, 05 §3] |
| task 이미지가 다르면 결과도 달라지나? | Pufferfish 동작은 컨테이너 바깥이라 그대로. 컨테이너 안 JVM 메모리 사용이 달라질 수 있어 JDK 7 이미지 대안 준비 (§3-4) |
| 공개 코드가 논문 실험 코드가 맞나? | 논문 p.263이 직접 지정한 저장소, 2018-02 이후 코드 변경 없음 |
| 왜 Docker를 이렇게 옛날 걸로? | 논문 명시 버전(1.12.1). 원 코드가 쓰는 `--oom-kill-disable` 등은 cgroup v1 + 당시 Docker 기준 |
| 하드웨어가 다른데 의미가 있나? | 절대값 비교는 불가. 같은 환경에서 baseline 대비 경향 확인이 목표 |
