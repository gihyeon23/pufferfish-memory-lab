# 랩미팅 (2026-10-05) — 2단계 로드맵: YARN 클러스터 + HiBench Kmeans

## 0. 현 위치

- 1~10차는 **1단계: 단일 노드 메커니즘 검증** → 완료
  (OCM 감지, suspend, puff, reclaim, EJF, 안전 하한선, swap headroom)
- 지금부터는 **2단계: 평가 환경 확장** — 메커니즘을 실제 클러스터 워크로드 위에서 측정
- 교수님께 설명할 때: "처음부터 다시"가 아니라 **"메커니즘 검증 완료 → 평가 환경으로 확장"**

## 1. 확정 사항 (9/30 정리본 기준)

| 항목 | 결정 |
|---|---|
| 워크로드 | **HiBench Kmeans** (논문 Fig 1, 6-a/b, 7-a/c, 12에서 최다 사용, 메모리 효과 최대) |
| 자원 관리자 | **최신 YARN** (control 1 + worker 2) — 논문 baseline = YARN 기본 동작 |
| controller 위치 | **A안: 외부 데몬** — YARN이 컨테이너를 띄우고, 각 worker에서 controller가 그 cgroup을 감시·조절 |
| 폐기 | MemoryGrowthWorkload를 평가 워크로드로 쓰는 것 (합성 워크로드 한계가 10차까지에서 드러남) |

- 현재 레포에 Hadoop/YARN/Spark/HDFS는 **코드·설정 모두 없음** (주석·문서 언급만)
- controller가 NodeManager 역할 + Pufferfish 역할을 축소판으로 겸하고 있던 상태

## 3. 작업 순서

### Step 0 — 호스트 기준선 측정 + 자원 예산 확정

- 현 호스트: MacBook Apple M4, 10코어 / 16GB, VirtualBox 7.2, 현재 VM 1대(2vCPU·4GB)
- 측정: macOS 유휴 시 실제 사용 중인 RAM, VirtualBox 오버헤드
- 9/30 안(control 2vCPU·3GB + worker 3vCPU·4GB ×2 = **8vCPU / 11GB**)은 16GB 호스트에 빡빡함
  - 제안: control **2vCPU·2GB**, worker **3vCPU·4GB ×2** = 8vCPU / **10GB** (macOS에 6GB 확보)
- **완료 기준**: VM 3대 합계 메모리와 macOS 여유분을 숫자로 적어 확정

### Step 1 — VM 3대 기동

> ✅ **완료 (2026-10-05)** — 실제 구성은 Bridged 대신 **NAT Network `pfnet`(10.10.0.0/24) + 포트포워딩**.
> 절차·검증 결과: [01-step1-vm-setup.md](01-step1-vm-setup.md)

- `control` / `worker1` / `worker2` (Ubuntu Server 24.04 ARM64)
- 네트워크: Bridged Adapter (7차 설계 그대로), `/etc/hosts`에 3대 상호 등록
- SSH 키 배포 (control → worker 무암호)
- 각 VM에서 `stat -fc %T /sys/fs/cgroup` → `cgroup2fs` 확인
- **완료 기준**: control에서 `ssh worker1 hostname`, `ssh worker2 hostname` 성공

### Step 2 — JDK 17 + Hadoop 3.5.0 설치, HDFS 기동

- 현 VM의 JDK는 **21** → 서버용 **JDK 17** 별도 설치 (`openjdk-17-jdk`), `JAVA_HOME` 고정
- `hadoop-3.5.0-aarch64.tar.gz` 설치, `core-site.xml` / `hdfs-site.xml` 구성
- `hdfs namenode -format` → NameNode(control) + DataNode(worker×2) 기동
- **완료 기준**: `hdfs dfsadmin -report`에 Live datanodes = 2

### Step 3 — YARN 기동, worker 2대 인식

- `yarn-site.xml`: ResourceManager(control), NodeManager(worker×2)
- NM당 자원 선언: `yarn.nodemanager.resource.memory-mb`, `.cpu-vcores`
- 이 단계에서는 **cgroup 설정은 아직 끄고** 기본(DefaultContainerExecutor)으로 시작 — 변수 최소화
- **완료 기준**: `yarn node -list`에 RUNNING 2대, `pi` 예제 MapReduce job 성공

### Step 4 — Spark on YARN 최소 동작 확인

- HiBench 전에 **SparkPi**부터 — Spark/YARN/JDK 조합 문제를 여기서 격리
- Spark 배포판은 "Pre-built with user-provided Hadoop" 또는 Hadoop 3.x 번들 중 선택
- **완료 기준**: `spark-submit --master yarn --deploy-mode cluster` 로 SparkPi 성공

### Step 5 — HiBench 빌드 + Kmeans tiny 실행

- 공식 레포가 아카이브됨 → **포크 또는 직접 패치 필요** (§5 리스크 참고)
- `hadoopbench` 전체를 빌드하지 말고 **Kmeans(sparkbench/ml)만** 선택 빌드해서 시간 절약
- `conf/hadoop.conf`, `conf/spark.conf`, `conf/hibench.conf` 구성
- `bin/workloads/ml/kmeans/prepare/prepare.sh` → `.../spark/run.sh`
- **완료 기준**: tiny 스케일 Kmeans가 YARN 위에서 성공하고 `report/hibench.report`에 수치가 남음

### Step 6 — 메모리 압박 지점 탐색

- 변수: HiBench 입력 스케일(tiny→small→large), `spark.executor.memory`, executor 수
- 기록 항목: job 완료시간, GC 시간, spill 바이트, 컨테이너 OOM-kill 여부, **CPU 사용률(3vCPU 병목 여부)**
- 목표: "executor 메모리를 줄이면 눈에 띄게 느려지거나 죽는" 구간을 찾아내 고정
- **완료 기준**: 메모리 압박이 재현되는 설정 1세트를 숫자로 확정

### Step 7 — baseline 측정 (논문의 "only admits one job")

- NM 자원을 조정해 **worker당 Kmeans 1개만** 수락되게 설정
- Kmeans 2~4개 동시 제출 → YARN이 나머지를 **pending(ACCEPTED)** 으로 두는지 확인
- 측정: 총 완료시간(makespan), 각 job 대기시간, 클러스터 실제 메모리 사용률(= 낭비분)
- **완료 기준**: "YARN 기본 = 자원이 남는데도 job이 대기한다"를 그래프/표로 제시

### Step 8 — controller를 YARN에 연결 (A안)

> 여기가 실제 구현량이 가장 큰 단계. 현재 controller는 **Docker에 결합**돼 있다.
> 읽기: `docker inspect` → PID → cgroup 경로 ([cgroup_utils.py:19-33](../../../controller/cgroup_utils.py#L19-L33))
> 쓰기: `docker update` ([puff_manager.py:135-145](../../../controller/puff_manager.py#L135-L145), [suspend_manager.py:52-56](../../../controller/suspend_manager.py#L52-L56))
> YARN 컨테이너는 Docker 컨테이너가 아니라 **일반 JVM 프로세스**이므로 그대로는 동작하지 않는다.

- **8-1. YARN cgroup v2 활성화**
  - `LinuxContainerExecutor` + `CgroupsLCEResourcesHandler` + `cgroups.v2.enabled=true`
  - `container-executor` 바이너리 권한·`container-executor.cfg` 세팅 (여기서 막히는 경우가 흔함)
  - v1 폴백이 조용히 일어나므로 **NM 로그에서 v2를 쓰는지 반드시 확인**
  - 컨테이너 cgroup 실제 경로 확인 (`.../hadoop-yarn/container_<id>`)
- **8-2. controller의 Docker 결합 제거**
  - "컨테이너 핸들" 추상화 도입: Docker 이름 ↔ YARN container cgroup 경로 둘 다 받게
  - 쓰기 경로를 `docker update` → `memory.max` / `memory.swap.max` / `cpu.max` / `cpuset.cpus` **직접 write**로 교체
  - 기존 Docker 경로는 회귀 테스트용으로 남겨둠
- **8-3. container_monitor를 동적 생명주기에 맞게 수정**
  - YARN 컨테이너는 수명이 짧고 계속 생성·소멸 → "컨테이너 이름 1개 폴링"에서 "cgroup 디렉터리 감시"로
- **8-4. admission 책임 재정의**
  - 지금의 `admission.py`는 "docker run 래퍼" → YARN에서는 **RM이 admission 주체**
  - 선택: (a) reclaim 트리거만 남기고 admission은 YARN에 위임, (b) §4.3.2(실사용량 기반 배치·delay)를 RM 플러그인 없이 외부에서 흉내
  - **이 선택은 Step 7 결과를 보고 결정**
- **완료 기준**: Kmeans 실행 중 OCM이 감지되고 puff/reclaim이 로그에 남음

### Step 9 — Pufferfish vs baseline 비교

- Step 7과 동일 조건에서 controller를 켜고 재측정
- 비교 지표: makespan, job 대기시간, 메모리 사용률, OOM-kill 횟수
- **완료 기준**: "YARN 기본 vs +Pufferfish" 비교표
