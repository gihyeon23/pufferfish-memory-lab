## 작업 1 — swap을 막으면 어떻게 되는가 (📋 실행 예정)

### 배경 (교수님 피드백)

- 쿠버네티스는 기본적으로 **swap을 사용하지 못하게 막는다**
  (kubelet이 swap 활성 노드에서 기동 거부, v1.22+ 부터 알파 기능으로 일부 완화)
- 따라서 **swap을 끈 조건에서 OOM killer가 실제로 도는지** 확인 필요
- 또한 **응답시간(timestamp)을 측정**하면, swap을 쓸 때 디스크 I/O 때문에
  시간이 크게 늘어나는 것이 보여야 한다

### 설계

**핵심: 호스트 swap을 끌 필요가 없다(sudo 불필요).** Docker에서
`--memory-swap`을 `--memory`와 **같은 값**으로 주면 그 컨테이너의 swap
할당량이 **0**이 되어 쿠버네티스 조건과 동일해진다.

| 조건 | docker 옵션 | 컨테이너 swap |
|---|---|---|
| A. swap 있음 (기존 실험) | `--memory=256m --memory-swap=768m` | 512MiB |
| B. swap 없음 (쿠버네티스 조건) | `--memory=256m --memory-swap=256m` | **0** |

> ⚠️ B 조건에서 `puff()`가 돌면 `SWAP_HEADROOM_MB=128`이 다시 붙어 swap이
> 생긴다. 따라서 **puff 없이 관찰만 하거나**, 실험용으로
> `SWAP_HEADROOM_MB=0`을 함께 적용해야 조건이 유지된다.

### 측정 항목

1. **OOM killer 동작 여부** — `memory.events`의 `oom`/`oom_kill`,
   `docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}'`
2. **OOM까지 걸린 시간** — A/B 조건 비교 (swap이 없으면 더 빨리 죽을 것)
3. **응답시간(핵심)** — 청크 할당 1회에 걸리는 시간

### 필요한 코드 변경 (이번 주 작업)

현재 `MemoryGrowthWorkload.java`는 **초 단위 timestamp만 찍고, 할당 1회에
걸린 시간(elapsed)은 측정하지 않는다.** swap 지연을 보이려면 이 측정이
필수다.

```java
// 현재: 타임스탬프만
logAllocation(memoryBean, allocationCount, config.chunkSizeMb, totalAllocatedBytes);

// 필요: fill() 소요 시간 측정 (swap-in/out이 여기서 발생)
long t0 = System.nanoTime();
byte[] chunk = new byte[(int) chunkSizeBytes];
fill(chunk);                                   // Arrays.fill = 전 페이지 터치
long elapsedMs = (System.nanoTime() - t0) / 1_000_000;
```

- `fill()`이 모든 페이지를 터치하므로, **swap-in이 필요하면 여기서 디스크
  I/O 지연이 그대로 드러난다**
- 밀리초 해상도 필요 (현재 timestamp는 초 단위라 부족)

### 예상 결과 / 가설

| 조건 | 예상 |
|---|---|
| A. swap 있음 | swap 사용 구간에서 **할당 1회 소요시간이 급증**(디스크 I/O), OOM은 늦게 발생하거나 회피 |
| B. swap 없음 | 소요시간은 일정하게 유지, 대신 **한도 도달 즉시 OOM-kill** |

→ "swap은 시간을 대가로 생존을 사는 것"이라는 trade-off를 정량적으로 제시할 수 있다.
이는 [pufferfish-architecture.md](../pufferfish-architecture.md) §2.5의
trade-off 표(무제한 swap + suspend vs. 고정 상한)와 직접 연결된다.

## 작업 2 — Pufferfish는 admission controller인가? (✅ 조사 완료)

### 결론: **아니다. "elastic memory manager"다.**

논문 원문(`docs/papers/pufferfish-paper.txt`) 직접 검증 결과:

**근거 1 — "admission"이라는 단어가 논문 전체에서 단 1회만 나온다**

유일한 등장(p.267, 평가 절)도 Pufferfish 설명이 아니라 **비교 대상인 Yarn의
동작 서술**이다:

> "Pufferfish enables a container parallelism of 2 during most of the
> application runtime while **Yarn only admits one job** (two 64GB Kmeans
> would exceed 120GB node capacity)."

**근거 2 — 초록이 스스로를 뭐라고 정의하는가**

> "We propose and develop Pufferfish, **an elastic memory manager**, that
> leverages containers to flexibly allocate memory for tasks. Memory
> elasticity achieved by Pufferfish **can be exploited by a cluster
> scheduler** to improve cluster utilization and task parallelism."

즉 **Pufferfish는 메모리 탄력성을 "제공"하는 쪽**이고, 그걸 이용해 배치
결정을 내리는 것은 **클러스터 스케줄러(YARN ResourceManager)의 몫**이다.

### "더 많은 컨테이너를 늘리는 것이 목적인가?" → 목적이 아니라 **결과**

논문이 밝힌 목적과 성과를 구분하면:

| 구분 | 내용 |
|---|---|
| **수단** | 컨테이너 메모리 탄력성 (OCM 감지 → suspend → puff/reclaim) |
| **목적** | OOM 회피 + 클러스터 메모리 이용률 향상 |
| **결과(성과 수치)** | 이용률 **2.7배**, median job runtime **5.5배** 개선 (초록) |
| **부수 효과** | container parallelism 증가, 큐잉 지연 감소 (p.259) |

즉 "컨테이너를 더 많이 띄우는 것"은 **탄력성으로 확보된 메모리를 스케줄러가
활용한 결과**이지, Pufferfish가 직접 admission 결정을 내리는 게 아니다.

### admission과 가장 가까운 동작은 있다 — 단, 보조 플러그인

§4.3.2 "Cluster Scheduler Plugin"에는 admission 유사 동작이 있다:

> "When scheduling a FLEX container, Pufferfish **delays the request** if it
> cannot be satisfied due to insufficient memory of a node, to avoid
> meaningless memory reclaim."

하지만 논문 스스로 이것을 **"20줄 미만의 휴리스틱"**("The heuristic
implementation requires less than 20 lines of code")이라고 서술한다 —
Pufferfish의 본체가 아니라 스케줄러에 얹는 보조 장치다.

### 우리 프로젝트에 대한 시사점

`controller/admission.py`라는 이름은 **"admission 시점(신규 컨테이너 실행
직전)에 reclaim을 트리거한다"**는 뜻이며, 이는 §4.3.1의

> "reclaim() is called whenever a new container is to be launched on the node"

를 재현한 것이라 **명명 자체는 정확하다.** 다만 발표에서
**"Pufferfish = admission controller"라고 말하면 틀린다** — 정확히는
"Pufferfish는 elastic memory manager이고, 그 reclaim 트리거 시점이
admission"이다.

## 작업 3 — EJF 우선순위 심화 (✅ 조사 완료)

### EJF의 정의와 근거 (p.264, §4.3.3)

> "**Earliest Job First (EJF)** policy prioritizes containers based on the
> **arrival time of the job** that the containers belong to. This is the
> **default policy** in Pufferfish. Its rationale is that the oldest job may
> release memory first."

### ⚠️ 핵심 발견: 논문은 우선순위를 **3곳**에 쓰는데, 우리는 1곳만 구현했다

| 용도 | 논문 근거 | 현재 프로젝트 |
|---|---|---|
| ① **puff backoff 비율** | p.263: 최우선 컨테이너가 기본 비율 `ϕ`, 2위는 `ϕ/Nc`, 3위는 `ϕ/(Nc)²`... | ❌ 미구현 (전부 동일 40%) |
| ② **puff 시 최저우선순위 kill** | Algorithm 1 lines 4–9: 노드 메모리가 꽉 찼는데 최우선 컨테이너가 OCM이면 최저우선순위 컨테이너를 kill | ❌ 미구현 (거부만 하고 안 죽임) |
| ③ **reclaim 순서** | p.264: "Reclaiming starts from the OCM container with the **lowest priority**" | ✅ 구현 (6차, EJF) |

→ **우리가 "EJF를 구현했다"고 하면 ③만 해당된다.** 발표에서 이 구분을
명확히 해야 한다.

### 우리 EJF의 근사(approximation)

- 논문: **job의 도착 시각** 기준 (YARN에서 하나의 job이 여러 컨테이너를 가짐,
  우선순위는 job 단위)
- 우리: **컨테이너 생성 시각**(`docker inspect .Created`) 기준
- 이유: 단일 호스트 실습에 **job 개념 자체가 없음** → 컨테이너 1개 = job 1개로
  간주한 근사
- 이 근사는 컨테이너가 1 job 1 container일 때만 논문과 일치한다

### 논문이 평가한 4가지 정책 (p.267, Figure 8)

| 정책 | 설명 | 결과 |
|---|---|---|
| **KILL** | 조율 없음. 각 컨테이너가 알아서 puff하고, 한 번의 puff로 요구를 못 채우면 kill | **최악** |
| **EJF** | 기본 정책. job 도착 시각 순 | 기준선 |
| **EJF+S** | EJF + suspension tolerance (너무 오래 suspend되면 kill 후 재배치) | EJF보다 개선 |
| **SJF** | 예상 완료 시간 짧은 순. starvation 방지를 위해 기본적으로 suspension tolerance 포함 | **90th percentile에서 최고 (EJF보다 23% 빠름)** |

**SJF가 EJF보다 빠른 이유**(p.267):
1. 짧은 job이 긴 job에 막히는 상황을 피함
2. 먼저 끝난 짧은 job이 긴 job을 위한 메모리를 빨리 반환

**SJF의 단점**(p.268): job 소요 시간의 **사전 지식(prior knowledge)이 필요**
→ 우리 프로젝트에서 미구현인 이유와 일치

### suspension tolerance (p.264)

> "We introduce **suspension tolerance** as the maximum duration a container
> can be suspended. A task will be **killed** if it is suspended longer than
> the suspension tolerance. By default, suspension tolerance is set to
> **half of the expected duration of a job**."

- 목적: 큰 메모리를 할당받고 오래 suspend된 FLEX 컨테이너의 메모리 낭비 방지
- SJF의 starvation 완화 장치이기도 함
- **현재 프로젝트 미구현** — suspend되면 무한정 suspend 상태로 남음
  (`suspend_manager.resume()`은 존재하나 아무도 호출하지 않음)

## 랩미팅에서 보고할 결론 (초안)

1. **Pufferfish는 admission controller가 아니라 elastic memory manager다.**
   "admission"은 논문 전체에 1회만 나오며, 그마저도 비교 대상 Yarn의 동작
   서술이다. 우리 `admission.py`는 "reclaim 트리거 시점이 admission"이라는
   의미이며 §4.3.1과 일치한다.
2. **컨테이너 수 증가는 목적이 아니라 결과다.** 목적은 OOM 회피 + 메모리
   이용률 향상(2.7배)이고, 늘어난 병렬성은 스케줄러가 탄력성을 활용한 결과다.
3. **EJF는 논문에서 3곳(puff backoff / puff kill / reclaim 순서)에 쓰이는데
   우리는 reclaim 순서 1곳만 구현했다.** 또 우리는 job 도착 시각 대신 컨테이너
   생성 시각을 쓰는 근사를 했다.
4. **swap 차단 실험은 쿠버네티스 조건을 재현하는 것이며**, 호스트 swap을 끄지
   않고 `--memory-swap = --memory`로 컨테이너 단위에서 동일 조건을 만들 수 있다.
5. 응답시간 측정으로 **"swap = 시간을 대가로 생존을 산다"는 trade-off를
   정량화**하는 것이 이번 주 핵심 실험이다.
