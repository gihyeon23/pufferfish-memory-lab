## 2. 말할 문장 (발표자 노트)

- 환경: "지난주에 말씀드린 원 저자 task 이미지를 x86에서 그대로 쓸 수 있게 돼서, 이제 OS·Docker·JDK까지 원 저자 환경과 같습니다. 메모리만 1/4로 줄였습니다."
- 관찰: "Spark executor 컨테이너가 한도를 넘자 CPU 1%로 멈추고, 컨테이너 크기가 정확히 1.4배씩 커지는 걸 로그로 확인했습니다."
- shrink: "논문은 실제 사용량에 2GB를 더해 줄인다고 했는데, 공개 코드는 1.1배를 곱합니다. 측정값도 1.1배 식과 정확히 맞았습니다. 원 코드 재현이 목적이라 그대로 두고, 결과 해석 때 밝히겠습니다."
- ★ 우리가 정한 값: "논문에 executor 코어 수가 없습니다. 논문은 'Spark와 Hadoop 기본 설정을 따르고 heap만 바꿨다'고 해서, Spark 기본값인 1코어로 정했습니다. 코어 수는 Pufferfish 규칙 자체는 안 바꾸지만, 메모리가 늘어나는 속도와 실행 시간을 바꿔서 OCM·puff 시점이 달라질 수 있습니다. 같은 설정으로 baseline과 비교하면 상대 비교는 유효합니다."
- HiBench: "논문과 원 코드에 HiBench 버전이 없어서, 원 저자 저장소 로그 날짜(2017년 2월) 당시 최신인 6.0을 골랐습니다."
- reclaim: "논문은 우선순위가 가장 낮은 컨테이너부터 회수한다고 강조하는데, 공개 코드는 멈춘 컨테이너들에서 똑같이 나눠 회수합니다. 앱이 둘 이상 동시에 멈출 때만 드러나는 차이라, Fig 6(b) 재현 때 직접 확인하겠습니다."

## 3. 예상 질문과 답

| 예상 질문 | 답 (근거) |
|---|---|
| 1코어면 논문보다 너무 느리지 않나? | 절대 시간은 원래 하드웨어가 달라 비교 불가. 같은 설정의 baseline 대비 상대 비교가 목표. 실행이 너무 길면 다시 정하겠다 (README §3-5) |
| 코어를 늘리면 결과가 달라지나? | Pufferfish 규칙(OCM 판정·×1.4·×1.1)은 그대로. 메모리 증가 속도·task별 메모리가 달라져 OCM·puff 시점과 최종 크기가 달라질 수 있음 [추측] |
| 왜 HiBench 6.0? | 버전 근거가 논문·원 코드에 없음. 원 저자 로그(2017-02) 시점엔 7.0이 없었음. 단 그 로그가 논문 실험인지는 모름 (steps/07 §2) |
| shrink ×1.1은 원 코드 버그인가? | 판단 못 함. 공개 코드와 실험 코드가 다를 수 있음 [추측] → 저자 문의 예정 |
| reclaim을 봤나? | 아직. launch 때 호출(`memory reclaim called`)만 확인, 노드 여유가 있어 회수는 없었음 → Fig 6(b)에서 확인 |
| 왜 VM 1대로 진행하나? | 3대 요청 중 1대 수령. 논문 §5.2 단일 노드 실험은 1대로 가능 → 먼저 진행 |
| 데이터 1/4이면 메모리 수요도 1/4인가? | 아님. 1/4은 시작값, 예비 실험(PR 1GB/16GB 힙)으로 조정 (steps/01 §6.1) |
| Fig 6(a)에서 kill이 왜 5번이나? | 우리 1/4 규모에선 KM 하나가 노드의 44%(논문 23%)를 써서 KM 2개가 서로 밀어냄 [추측]. kill 대상은 원 코드대로 "가장 늦은 앱 중 Flex 컨테이너가 있는 앱" (steps/09 §5) |
| 재시작이 막힌 건 어떻게 아나? | RM 로그 `memflexn actual memory give up` 373회. 원 코드 RM이 노드 실제 여유가 요청의 2배 미만이면 Flex 배정을 미룸 (`LeafQueue.java:1551-1569`) |
| PR이 단독보다 느려진 이유? | KM과 CPU·디스크(swap)를 나눠 쓰고, 노드가 찬 동안 puff가 멈춰서 [추측] |
| JDK 7/8 비교는? | 원 이미지(JDK 7u51)를 그대로 쓰게 돼서 취소 |
